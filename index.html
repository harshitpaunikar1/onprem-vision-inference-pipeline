On-Prem Multimodal Extraction System

Schema-Bound Vision Intake for Sensitive Operations

Manual review is the first problem, not the last step. When every incoming image waits for a person to open it, interpret it, type fields into a system, and decide whether the picture is clear enough to trust, operations slow down exactly where the data is most sensitive. The review queue becomes the integration layer, the quality gate, and the audit trail by accident. It also becomes the point where private images remain visible longer than they should. The system described here replaces that accidental workflow with a deliberate one: secure on-prem image intake, prompt-configured extraction using Gemma 3 and Llama 3.1, JSON-schema validation, deterministic normalization, and explicit rejection paths.

The point is not to ask a model for “JSON if possible.” The point is to turn images into structured records that can be accepted, repaired, or rejected under contract. That requires an API edge that buffers and authenticates uploads, a prompt registry that dispatches the correct task template, a validation layer that treats malformed or underspecified output as a first-class failure, and a control plane that lets operators change templates, run A/B tests, inspect drift, and iterate weekly without redeploying the entire stack.

Deployment Gemma 3 and Llama 3.1 run on secure on-prem servers so image payloads never leave the controlled network boundary.
Acceptance Rule Only schema-valid JSON reaches structured-output dispatch and database persistence.
Operational Loop No-code prompt configuration, A/B testing, monitoring, and weekly iteration tune extraction behavior without code churn.
Failure Boundary Rejected outputs are routed to a review queue with traceable error classes instead of being silently patched downstream.

This article follows the pipeline in the order an operator cares about it: the human bottleneck first, then intake, prompt dispatch, validation, post-processing, and finally the mechanics of rejection and control-plane change. The visual language stays black and white because the architecture itself should carry the emphasis.

I

Clause I

The Manual Review Bottleneck Shall Be Named Before the Model

Most extraction projects are introduced with model names, benchmarks, or enthusiasm about multimodality. That sequence hides the actual operational failure. In a manual process, a reviewer receives an uploaded image, decides what task it belongs to, zooms and pans until the relevant region is visible, transcribes key fields into an application, and then makes a private judgment about whether the record is complete. Throughput is constrained by attention, not compute. The person reviewing the image also becomes the one exposed to every sensitive detail inside it, whether that detail is needed for the downstream record or not. In practice, the queue grows during peak periods, service-level expectations become uneven, and every batch inherits variance from reviewer habits.

A useful extraction system starts by removing that accidental dependence on individual interpretation. It does not attempt to eliminate people from the workflow entirely. It narrows their role to explicit exceptions. That design decision changes the architecture. Instead of sending every image to a reviewer and later adding automation, the system accepts every image into a governed intake path, attempts schema-bound extraction, and only creates a human task when one of the control conditions fails: unsupported image type, low confidence on a critical field, enum mismatch, impossible date, missing required evidence, or policy-triggered escalation. Review then becomes scarce and targeted rather than universal and routine.

This is why the acceptance test cannot be “the output looks plausible.” Plausible text still forces manual correction and still leaves downstream consumers guessing which fields are trustworthy. The operating objective is narrower: produce records that can enter the database without additional interpretation, or reject them early enough that the rejection reason is informative. Sensitive-data exposure drops because only failed cases stay visible to human reviewers. Operational latency drops because the standard path is machine-handled. Consistency improves because the same extraction contract is applied to every request in the same task family. Once that problem statement is stated precisely, the rest of the architecture becomes less theatrical and more disciplined.

Review Becomes Exception-Only

The system assumes three states, not two.

  • Accept: schema-valid and policy-clean.
  • Repair: normalization can fix form without changing meaning.
  • Reject: manual review required.
II

Clause II

Image Intake Must Stabilize the Record Before Inference Begins

The API gateway is not a thin proxy in this design. It is the first enforcement point. Incoming images arrive from scanners, mobile capture flows, or internal applications and are buffered at the edge so a client does not have to hold an open connection while inference runs. The gateway authenticates the caller, stamps a request identifier, records tenant and task metadata, verifies MIME type, rejects oversized payloads, and stores a normalized object reference for the image or page bundle. If the upload contains multiple pages, page boundaries are resolved before model dispatch; otherwise the downstream layers inherit ambiguity they cannot cleanly undo.

Two details matter here. First, task identity is explicit. The request should say whether the job is, for example, label_extract, form_extract, or damage_report_extract. The pipeline should not infer the task family from the picture itself when the caller already knows the business intent. Second, intake should separate transport metadata from extraction targets. Caller identity, upload timestamps, source system, and routing rules belong to the envelope. Extracted business fields belong to the schema payload. Keeping those concerns separate makes auditing simpler and reduces the temptation to stuff operational fields into model output.

Once the image envelope is stable, the gateway can forward a compact internal job description into the extraction queue: object location, task id, schema version, prompt experiment key, and required service-level tier. That record is small enough to retry safely, index for monitoring, and hand to a model worker without resending the original image bytes through multiple services. If the system needs to throttle, deduplicate by content hash, or quarantine corrupted uploads, the gateway is the correct place to do it.

Gateway Contract

  • Authenticate before buffering.
  • Assign a stable request id before queueing.
  • Carry task id and schema version with the job.
  • Keep raw image bytes out of downstream logs.
III

Clause III

Prompt-Configured Extraction Is a Dispatch Contract, Not a Chat Session

Once the intake record is stable, the worker does not improvise. It resolves a template from a registry keyed by task id, schema version, and experiment flag. That registry is the practical center of the system because it turns “prompt engineering” into an operational artifact rather than developer folklore. A template defines the instruction block, required field definitions, allowed abstentions, formatting rules, and model preference. It can also define task-specific guardrails such as “never guess missing serial numbers,” “return one record per page,” or “if the image is unreadable, emit a rejection object rather than a partial payload.” Those are not decorative reminders. They are constraints that reduce ambiguity at the exact point where ambiguity would become expensive.

Gemma 3 and Llama 3.1 can be hosted behind the same internal worker pool while serving different operating profiles. One template may route to Gemma 3 because the task is narrow and latency-sensitive; another may route to Llama 3.1 because longer instruction context or richer visual reasoning is worth the cost. The routing rule should live next to the template definition, not in scattered application logic, so A/B tests can compare template revisions without rewriting client code. A no-code configuration surface matters here because extraction owners are often operations or product teams who understand failure cases but should not have to cut deployments just to update wording, tweak a negative example, or change the threshold for a fallback path.

The discipline to preserve is simple: the model only sees what it needs. The worker sends the image reference, the selected instruction block, the explicit schema description, and no extraneous operational chatter. It also refuses unsupported combinations before inference. If a task requests a schema version that has been retired, or the prompt experiment key is not allowed for that tenant, the worker rejects the job without spending model time. This keeps prompt configuration close to policy and keeps the inference layer honest about what it can and cannot do.

template = registry.resolve(
    task_id=request.task_id,
    schema_version=request.schema_version,
    experiment_key=request.experiment_key,
)

if template is None or not template.enabled:
    raise Reject("template_not_available")

if request.mime_type not in template.allowed_mime_types:
    raise Reject("unsupported_media_type")

model_id = template.model_preference  # "gemma-3" or "llama-3.1"
prompt = build_guarded_prompt(template, image_ref=request.object_ref)
candidate = inference.run(model_id=model_id, prompt=prompt)

That small dispatch block captures the real posture of the system. The template is versioned, the media type is checked, the model choice is explicit, and the output is merely a candidate until validation completes. Prompting matters, but only inside the larger contract.

IV

Clause IV

Schema Validation Defines Success, Repair, and Refusal

JSON validity alone is insufficient. A model can return syntactically valid JSON that still violates the business contract: missing required fields, impossible dates, inconsistent page counts, free-text labels where enums are required, numeric values outside allowed range, or confidence values present for optional fields but absent for critical ones. For that reason the pipeline validates in layers. The first layer checks that the payload parses and matches the top-level shape. The second layer evaluates field requirements, enum membership, and cardinality. The third layer runs semantic rules that the schema cannot express cleanly on its own: start date cannot exceed end date, extracted total must equal the sum of normalized line items within tolerance, and a task marked unreadable cannot also claim high-confidence values for critical fields.

The schema should also preserve provenance. When a field matters, the output record can carry both a normalized value and evidence about where that value came from: page index, region hint, raw span, or extraction confidence. This is useful for audits and for manual review because it lets a reviewer inspect the exact claim that failed instead of reopening the whole image without context. The system still stores only the fields it intends to use; provenance exists to explain acceptance, not to excuse weak extraction. If the evidence is missing for a mandatory field, the record is incomplete even if the text looks plausible.

Repairable failures are limited and explicit. Trimming whitespace, normalizing date format, uppercasing a controlled code, or converting a decimal string into a numeric type can happen after schema validation identifies a safe transformation. Repair does not mean inventing values. If the candidate omits a required field or returns a label that is semantically outside the allowed domain, the proper result is rejection. That clarity is what prevents downstream systems from inheriting half-trusted payloads that later require human cleanup.

Field Discipline

  • Required fields fail closed.
  • Enums reject near-matches unless mapped in policy.
  • Confidence without provenance is not enough.
  • Repair may transform format, not meaning.
validator = Draft202012Validator(EXTRACTION_SCHEMA)
errors = sorted(validator.iter_errors(candidate), key=lambda err: list(err.path))

if errors:
    raise Reject(
        code="schema_contract_failed",
        details=[{"path": list(err.path), "message": err.message} for err in errors],
    )

normalized = normalize(candidate)
semantic_errors = check_business_rules(normalized)
if semantic_errors:
    raise Reject(code="semantic_contract_failed", details=semantic_errors)
V

Clause V

Post-Processing Owns Canonical Form, Audit Fitness, and Database Readiness

Post-processing exists because the database contract is usually stricter than the extraction contract. Even a valid record may need canonicalization before it can be written safely into operational tables. Dates must be rendered into one standard. Controlled labels need mapping to internal codes. Numeric fields may need unit normalization. Repeating groups may need deterministic ordering. Empty strings should become nulls where the target schema expects absence rather than blank text. This layer must be boring by design. If it becomes a hidden machine-learning stage, the system loses traceability.

A disciplined post-processor also carries forward the audit envelope created at intake. The final structured-output dispatch should include the request id, task id, schema version, prompt template version, selected model, and the acceptance timestamp. Those fields are what let the team compare prompt variants later, explain why a specific record was accepted, and roll back a template if a weekly iteration introduces a regression. The API gateway may be the component that ultimately pushes to the database, but it should do so only after receiving an accept-class payload whose shape is already stable.

Fallback behavior belongs here as well. If a non-critical optional field fails normalization, the record may still be accepted with a warning flag. If a target system is temporarily unavailable, dispatch should queue the already-accepted payload for retry rather than rerun inference. That distinction matters because model execution is probabilistic and expensive relative to replaying a validated record. The more sharply the system separates extraction from post-processing, the easier it becomes to reroute accepted output to new downstream consumers without reopening image interpretation logic.

  • NormalizeConvert dates, numeric strings, and controlled labels into canonical storage formats.
  • AnnotateAttach request id, model id, template version, and acceptance class for monitoring and audit.
  • DispatchPush accepted records to the database or buffer them for write retry without re-inference.
  • WarnMark optional-field degradation explicitly instead of folding it into silent data loss.
VI

Clause VI

Error Handling Must Exit Through Deliberate Branches Rather Than Hidden Heuristics

An extraction pipeline fails in more ways than “the model was wrong.” Some images arrive corrupt. Some are technically readable but do not match the declared task. Some produce parseable JSON with unusable semantics. Some satisfy the schema and still violate policy because a critical field is low-confidence or the image content falls into a class that must always be reviewed manually. Treating these states as one generic failure leads to generic retries, noisy monitoring, and reviewer queues that provide no clue what needs attention.

The better pattern is a typed rejection ledger. Each failed job exits with a code, a severity, the stage at which it failed, and the evidence needed for a human or a follow-up process to act on it. A parse failure might indicate a prompt problem or a model format issue. A structural contract failure might indicate a schema mismatch after a prompt template change. A semantic failure might indicate that the image family itself needs a different task template. A policy rejection may be perfectly valid extraction from the model’s perspective but still require manual review because the task falls under a compliance rule. Those distinctions make the queue actionable.

Retries should also respect failure type. Transport and storage failures are retryable. Prompt resolution failures are usually configuration issues and should page the operator rather than loop. Parse failures might be retried once on a secondary template or alternate model if the task configuration explicitly allows it. Semantic contradictions should not be “retried until lucky”; they should be reviewed because repeated probabilistic attempts tend to produce different wrong answers rather than a principled correction. The rejection branch therefore needs equal design attention as the acceptance branch. It is where trust is preserved.

Rejection Ledger

  • Stage: intake, dispatch, parse, schema, semantic, policy, writeback.
  • Code: stable machine-readable identifier.
  • Evidence: failing field path or policy trigger.
  • Action: retry, repair, or manual review.
VII

Clause VII

The Control Plane Governs Prompt Change, A/B Testing, and Weekly Iteration

The runtime path above is only half the system. The other half is the control plane that decides how templates evolve without destabilizing production. In this project, prompt configuration is intentionally exposed through a no-code surface so task owners can edit task-specific templates, maintain guardrails, and promote new revisions into experiment slots. That surface should not be confused with unconstrained prompt editing. It operates on typed records: template body, supported schema versions, allowed models, fallback behavior, and evaluation notes. A change is meaningful only if it can be compared against a baseline on a test set and then observed in production.

A/B testing is therefore not a marketing metaphor here. It is a formal method for deciding whether template revision B improves acceptance rate, reduces schema failures, or lowers manual-review volume relative to revision A for the same task family. Because the gateway and dispatch layers record template version and model id with every accepted or rejected record, weekly review can examine the exact slices that matter: which task ids are drifting, which schema fields create the most rejections, whether Gemma 3 is sufficient for the fast path, and where Llama 3.1 is paying for itself in reduced exception volume. Monitoring should track queue depth, per-stage latency, rejection code distribution, and manual-review share over time. Those are the signals that tell the team whether the extraction contract is tightening or fraying.

The control plane also owns rollback discipline. If a new prompt revision increases parse failures for one task, the operator should be able to pin that task back to the last known-good template without touching unrelated flows. If a schema version changes, the release should show exactly which fields were added, renamed, or made mandatory, and which downstream consumers will notice. Weekly iteration only works when version history is visible, comparison runs are reproducible, and production monitoring can be segmented by template, model, tenant, and task family. Otherwise the team is still operating by anecdote, just with faster models.

The control plane is also where visual distinctness between projects should be preserved when the broader portfolio is expanded. This page uses a monochrome contract-spine treatment because the subject is governed flow and acceptance logic. The next project in the queue should not inherit that structure by default; it should express its own operating pressure. That is why the system closes here rather than with another model flourish. A reliable multimodal extraction pipeline is not the sum of a model and a prompt. It is the sum of bounded intake, explicit task dispatch, schema-governed acceptance, deterministic post-processing, typed rejection, and a change-management surface that can iterate every week without eroding trust.

Operational Close

The article leaves one implementation truth in plain view: JSON is not the product, accepted records are. Everything before the schema gate is an attempt. Everything after it is controlled business data. That distinction is what makes on-prem multimodal extraction operationally useful rather than merely impressive in a demo.
